# 校园跑腿互助平台 PRD

- 文档版本：V1.0
- 阶段：需求定义 / 静态展示
- 产品名称：校园搭把手（Campus Errand）
- 当前状态：仅静态展示；无真实账号、订单后端、支付或消息服务

## 1. 项目背景与问题

校园内存在大量低复杂度、短距离、时间敏感的互助需求，例如代取快递、顺路带餐、借送学习用品。现有沟通方式分散在群聊、社交平台和熟人网络中，常见问题包括需求描述不完整、任务状态不透明、双方信任不足、取消或争议后缺乏处理记录。

平台希望把需求整理为标准化任务，并用清晰的订单流程和适度的信用记录帮助学生进行互助。

## 2. 产品目标

### 2.1 用户价值
- 发布者：更快找到愿意帮忙的同学，明确任务范围、时间和费用。
- 接单者：发现顺路任务，提前了解工作量和回报。
- 校园社区：沉淀可解释的履约记录，减少沟通成本。

### 2.2 MVP 目标
1. 用户能理解平台定位、使用流程与安全边界。
2. 任务信息以统一结构展示。
3. 明确发布、接单、完成、取消、举报等关键业务规则。
4. 在进入真实运营前验证需求，不将静态页面误认为可交易服务。

### 2.3 非目标（当前版本）
- 不提供真实用户注册、身份认证或权限管理。
- 不支持真实任务创建、接单、私信、订单状态同步。
- 不收款、不托管资金、不提供保险或纠纷裁决。
- 不声称示例用户、任务、报酬或数据是真实的。

## 3. 目标用户与场景

### 3.1 任务发布者
有临时、短距离、低风险需求的在校学生；希望快速说明需求并确认任务完成。

### 3.2 任务承接者
有空闲时间或本来就要经过相关地点的学生；希望了解耗时、路线、物品要求与报酬后再决定。

### 3.3 管理员 / 校园运营
负责处理举报、异常订单、滥用行为、规则更新和争议复核。MVP 阶段可先采用人工流程。

## 4. 信息架构

1. 首页：平台定位、核心价值、流程、安全说明。
2. 任务大厅：任务卡片、类别、地点区域、截止时间、预估耗时、报酬、状态。
3. 任务详情：完整描述、双方要求、取送区域、截止时间、费用、取消规则。
4. 发布任务：类别、标题、描述、取送地点、时间、报酬、备注。
5. 我的任务：我发布的、我承接的、已完成、已取消、争议中。
6. 信用与评价：履约记录、评价、取消记录和申诉入口。
7. 帮助与安全：禁止任务、隐私规则、举报、申诉与常见问题。

## 5. 核心用户流程

### 5.1 发布任务
填写表单 → 校验必填项与规则 → 发布成功 → 等待承接 → 与承接者确认细节 → 完成后确认。

### 5.2 承接任务
浏览 / 筛选 → 查看详情 → 申请承接 → 发布者确认（或采用明确的抢单规则）→ 双方确认要求 → 执行 → 提交完成 → 双方评价。

### 5.3 取消与争议
发起取消 → 选择原因 → 根据任务状态及取消规则处理 → 通知另一方 → 如存在争议则冻结评价/信用影响 → 人工复核 → 记录结果。

## 6. 订单状态设计

- 草稿：任务尚未公开。
- 待承接：任务已发布，尚无人承接。
- 待确认：有学生申请，等待发布者确认（可选流程）。
- 进行中：双方确认，任务执行中。
- 待完成确认：承接者提交完成，等待发布者确认。
- 已完成：任务完成，允许双方评价。
- 已取消：任务终止，记录取消原因。
- 争议中：存在举报或双方对完成情况有分歧，等待复核。

状态变更需有权限约束与操作日志。已完成或已取消的任务不可直接回到待承接；争议结论由人工复核，不应仅靠模型或评分自动决定。

## 7. 功能需求与优先级

| 功能 | 优先级 | 验收要点 |
|---|---|---|
| 首页与产品介绍 | P0 | 桌面及手机布局正常；明确标注当前是静态演示 |
| 任务卡片与大厅 | P0 | 显示类别、标题、耗时、报酬与示例状态 |
| PRD 与项目路线 | P0 | 仓库可直接阅读文档 |
| 任务筛选 | P1 | 可按类别、区域、时间和报酬筛选 |
| 任务详情 | P1 | 展示完整要求、费用、限制和取消规则 |
| 发布任务表单 | P1 | 校验必填项、时间、合理描述与禁止内容提示 |
| 接单与状态管理 | P1 | 状态迁移合法且可追踪 |
| 登录与身份验证 | P2 | 仅收集必要信息，明确数据用途和保存周期 |
| 评价与信用 | P2 | 双向评价、反滥用机制、申诉与人工复核 |
| 举报与管理后台 | P2 | 举报分类、处理状态、审计日志与申诉路径 |
| 支付 / 退款 | 暂缓 | 需先评估法律、支付、资金托管和争议处理要求 |

## 8. 任务字段

- task_id：唯一任务标识。
- title：标题，建议 5–40 字。
- category：任务类别。
- description：任务描述。
- pickup_area / delivery_area：取件与交付区域；公开列表应避免暴露精确宿舍门牌。
- deadline：期望完成时间。
- estimated_duration：预估耗时。
- reward：约定报酬；上线前需明确费用规则与争议处理。
- publisher_id / runner_id：发布者与承接者标识。
- status：订单状态。
- created_at / updated_at：创建和更新时间。
- cancellation_reason / dispute_status：取消和争议信息。

## 9. 信用体系原则

信用记录应可解释、可申诉，避免只依据单一分数判断用户。可考虑的信号包括已完成订单、双方确认、无故取消、有效举报与复核结果。对于争议中的订单，应暂缓产生负面信用影响；对新用户提供合理的起步机会，避免冷启动歧视。不得公开不必要的个人资料或未经核实的指控。

## 10. 安全、隐私与内容边界

- 禁止违法、危险、违规代购、代签、账号密码交付等任务。
- 公开页面不显示手机号、宿舍门牌、证件或敏感个人信息。
- 只收集完成任务所需的最少数据，并说明用途、访问权限与删除机制。
- 对线下交接提供基本安全提醒；不鼓励前往偏僻地点或单独处理高风险任务。
- 建立举报、屏蔽、申诉和人工复核流程。
- 真实上线前应评估学校规定、当地法律、未成年人保护、支付及个人信息保护要求。

## 11. 当前页面与技术范围

当前实现为纯 HTML/CSS 静态站点，可通过 GitHub Pages 发布：
- `index.html`：响应式产品介绍页。
- `docs/PRD.md`：本产品需求文档。
- `.github/workflows/pages.yml`：自动部署配置。

当前不包含后端、真实数据库、身份验证、订单 API、支付或通知功能。界面示例数据均为虚构展示内容。

## 12. MVP 验收标准

1. 首页可在常见桌面和移动端浏览器正常访问。
2. 导航链接可跳转至对应页面区块。
3. PRD 链接可打开完整文档。
4. 仓库为公开，部署工作流可运行。
5. 首页显著说明任务数据为示例、当前不处理真实订单。
6. 无明显水平溢出、不可读文本或失效的内部链接。

## 13. 后续迭代路线

- V0.1：静态产品页、示例任务、PRD、GitHub Pages 部署。
- V0.2：可交互前端原型，加入筛选、详情页和发布表单（本地模拟）。
- V0.3：后端 API、持久化数据、账号体系和订单状态机。
- V0.4：举报、申诉、人工审核、信用与评价机制。
- V1.0：校园试点、可用性测试、安全评估、监控和运营流程。

## 14. 待验证问题

- 学生最常见、最愿意付费/互助的任务类别是什么？
- 校园内合理报酬和取消规则如何制定？
- 需要何种学生身份验证，哪些信息不应收集？
- 任务承接采用申请确认还是先到先得？
- 争议、物品损坏、未按时完成的处理边界如何定义？
- 学校政策是否允许此类互助服务，以及是否涉及商业经营或支付合规问题？
