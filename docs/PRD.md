## 1. 文档说明

### 1.1 文档目的

本 PRD 用于统一产品目标、功能范围、关键交互、业务规则、异常处理及验收标准，为后续原型设计、开发实现和测试提供依据。

### 1.2 当前产品状态

目前项目为部署在 GitHub Pages 上的静态展示网站。页面中的任务、用户和报酬均为示例数据；当前不支持真实注册、任务发布、接单、消息、支付或订单持久化。本文描述的是目标产品方案，不代表相关功能已经上线。

### 1.3 文档分工

- **本 PRD：** 定义产品范围、功能需求、交互要求、业务规则、AI 辅助能力边界和验收标准。
- **需求调研报告：** 记录市场桌面研究、问卷方案、用户画像假设、竞品观察及调研验证计划。
- 为避免重复维护，用户画像、市场规模背景和竞品详情以需求调研报告为准；本 PRD 仅引用其对产品决策有直接影响的结论。

## 2. 产品概述

### 2.1 项目背景

校园内存在取快递、顺路带物、交接普通学习用品等短距离生活互助需求。现有求助渠道通常依赖群聊或熟人网络，任务信息不易检索，时间、地点、报酬和交付要求可能表达不完整，任务状态及取消争议也缺少统一记录。

产品希望将此类低风险需求组织成标准化任务，帮助发布者说明需求，帮助承接者判断任务是否适合自己，并通过清晰的状态、履约记录和申诉机制降低协作摩擦。

### 2.2 产品定位

面向同一校园或校区学生的轻量互助任务平台。产品优先强调校园场景适配、任务信息清晰、顺路协作、隐私保护和规则透明；首期不与综合即时配送平台竞争全品类覆盖和专业运力。

### 2.3 产品核心目标

1. **降低发布成本：** 让用户以结构化字段快速描述任务，减少反复沟通。
2. **提高匹配效率：** 让承接者在决策前看到任务类别、区域、截止时间、预计耗时和报酬。
3. **提升履约可见性：** 通过明确的订单状态、操作记录和完成确认，减少信息不对称。
4. **建立可解释的信任机制：** 记录履约事实，提供举报与申诉渠道，不以单一评分或模型判断直接处罚用户。
5. **验证真实需求：** 先完成问卷、访谈和原型测试，再决定是否进入真实运营。

### 2.4 目标用户

- **任务发布者：** 有临时、短距离、低风险需求的在校学生。
- **任务承接者：** 有空闲时间或顺路经过相关区域的在校学生。
- **平台运营/审核人员：** 处理违规内容、用户举报、异常任务和争议申诉。

同一学生可在不同任务中分别担任发布者和承接者。

### 2.5 产品范围与非目标

**本期规划范围**
- 首页、任务大厅、任务详情、发布任务、我的任务、履约记录、帮助与安全说明。
- 任务筛选、状态管理、取消原因、完成确认和评价申诉的规则设计。
- AI 辅助完善任务描述和提示潜在风险的可选方案，需经过验证后才进入实现。

**当前不包含**
- 真实账号、校园身份认证、实时私信、真实订单后端与数据库。
- 真实支付、资金托管、保险、自动退款或自动争议裁决。
- 对危险、违法、违规代购、代签、账号密码交付、高价值物品或敏感资料的任务提供撮合。
- 将示例数据或未验证的用户假设表述为真实业务结果。

## 3. 产品架构与信息架构

### 3.1 产品核心架构

产品按用户交互、业务规则和服务支撑三层规划：

1. **交互层：** 首页、任务大厅、任务详情、发布表单、我的任务、履约记录、帮助与安全。
2. **业务层：** 任务发布校验、任务检索与筛选、接单确认、订单状态机、取消与争议流程、评价与信用记录。
3. **服务支撑层（后续阶段）：** 身份与权限、数据持久化、通知、举报工单、审计日志、AI 辅助服务及运营管理工具。

当前静态网站仅实现交互层中的展示内容，不具备上述后端业务能力。

### 3.2 信息架构

- **首页：** 产品定位、主要价值、使用流程、当前版本说明。
- **任务大厅：** 任务列表、类别/区域/时间筛选、任务状态。
- **任务详情：** 任务描述、交付区域、截止时间、预计耗时、报酬、注意事项及取消规则。
- **发布任务：** 任务字段填写、规则提示、内容检查与发布确认。
- **我的任务：** 我发布的、我承接的、待处理、进行中、已完成、已取消和争议中。
- **履约记录：** 已完成记录、双方评价、取消记录及申诉状态。
- **帮助与安全：** 禁止任务、隐私说明、举报、申诉及常见问题。
- **运营管理（后续）：** 举报队列、争议处理、内容审核、操作日志与规则配置。

## 5. 产品设计

### 5.1 产品核心目标和架构

本产品以“任务发布—任务匹配—履约执行—完成确认—信用沉淀”为核心业务闭环。产品架构应优先保障任务信息的完整性、状态流转的一致性和异常处理的可追溯性，而不是单纯增加功能数量。

核心业务模块：
- **任务管理：** 创建、展示、筛选、编辑限制、取消和状态追踪。
- **匹配与承接：** 根据任务条件帮助用户发现任务，由用户自主判断并确认承接。
- **履约管理：** 明确执行要求、完成提交和发布者确认。
- **信任与治理：** 履约记录、双向评价、举报、申诉、人工复核。
- **智能辅助（可选）：** 帮助用户补全描述、检查信息缺失并提示潜在风险；不替代用户决策或人工审核。

### 5.2 设计功能

以下按用户任务组织功能说明。每项包含设计目标、触发路径、交互流程、页面要求及验收重点；AI 能力另设专节，避免在每项功能中重复描述。

#### 5.2.1 任务大厅与筛选

**设计目标**
帮助用户快速发现当前可承接、且在时间和区域上适合自己的任务。

**触发路径**
首页 →「任务大厅」→ 选择类别、区域、截止时间或报酬范围。

**交互流程**
1. 默认展示可查看的任务卡片。
2. 用户选择一个或多个筛选条件。
3. 列表更新，并显示当前筛选条件。
4. 用户可清除单项条件或重置全部筛选。
5. 点击任务卡片进入详情页。

**页面设计**
- 卡片优先展示标题、类别、区域级位置、截止时间、预计耗时、报酬和状态。
- 不在公开列表显示精确宿舍门牌、手机号或其他非必要个人信息。
- 加载、无结果、筛选条件冲突和数据获取失败时均应有明确反馈。
- 任务列表需在窄屏设备上保持可读，不依赖仅颜色表达状态。

**验收重点**
- 多条件筛选结果一致且可清除。
- 无结果时提供清除筛选的入口。
- 已取消、已完成或争议中的任务不应被误展示为可承接任务。

#### 5.2.2 任务详情

**设计目标**
让用户在承接前理解任务内容、时间要求、工作量、费用和限制，降低后续误解。

**触发路径**
任务大厅 → 点击任务卡片 → 任务详情。

**交互流程**
1. 展示任务完整信息及当前状态。
2. 用户查看交付区域、截止时间、预计耗时、报酬、任务说明和安全提醒。
3. 若任务仍可承接，符合条件的用户可选择申请承接。
4. 若任务状态已变化，页面提示最新状态并禁用过期操作。

**页面设计**
- 按“任务内容、时间与地点、费用与交付、规则与安全”分组展示。
- 对报酬和费用承担方式使用明确文案，避免暗示费用已托管。
- 展示创建时间与必要的状态变化记录。
- 对风险提示提供可理解的原因，不仅显示笼统的“无法操作”。

**验收重点**
- 关键字段完整呈现。
- 状态变化后，过期的承接操作不可提交。
- 用户能够找到取消规则和举报入口。

#### 5.2.3 发布任务

**设计目标**
让发布者以尽可能少的操作提供足够信息，使潜在承接者能够评估任务是否可行。

**触发路径**
首页或任务大厅 →「发布任务」→ 填写表单 → 预览 → 确认发布。

**交互流程**
1. 选择任务类别并填写标题、描述、取送区域、期望完成时间、预计耗时和报酬。
2. 前端检查必填项、时间格式、字段长度和明显不合理的输入。
3. 如启用 AI 辅助，先由用户主动触发检查；系统仅提供建议，不未经确认自动发布。
4. 用户查看预览，确认信息和规则后提交。
5. 成功后进入任务详情或「我的任务」，状态为“待承接”；失败时保留已填写内容并说明原因。

**页面设计**
- 必填项与选填项区分清楚，提供简短示例和字段说明。
- 位置优先选择区域或公共交接点；不要求公开精确宿舍门牌。
- 费用、截止时间和交付要求在预览页突出显示。
- 对禁止任务提供明确说明和修改指引。
- 当前原型阶段提交只产生本地模拟结果，不向用户暗示数据已保存到服务器。

**验收重点**
- 必填字段缺失时不能提交。
- 错误提示定位到具体字段。
- 提交失败时已填写内容不丢失。
- 发布前用户必须有机会核对任务内容。

#### 5.2.4 申请承接与确认

**设计目标**
确保承接者在了解任务条件后自愿申请，并由相关用户明确确认任务责任和交付约定。

**触发路径**
任务详情 →「申请承接」→ 确认任务条件 → 等待发布者确认 → 进入进行中。

**交互流程**
1. 系统检查任务是否仍为可承接状态。
2. 承接者确认预计耗时、截止时间、报酬及交付要求后提交申请。
3. 发布者查看申请并确认一位承接者。
4. 系统将任务状态变为“进行中”，并通知双方查看最终任务要求。
5. 若任务已被他人承接或已取消，系统拒绝重复操作并解释原因。

**页面设计**
- 操作按钮需清晰区分“申请承接”“确认承接”“取消申请”等不同动作。
- 提交前展示重要条件；关键状态变化需有确认反馈。
- 在后端版本中使用事务或等效并发控制，避免同一任务被重复确认给多人。

**验收重点**
- 非法状态不能承接。
- 同一任务同一时间只允许一个有效承接关系，除非未来明确支持多人任务。
- 申请与确认结果可追踪。

#### 5.2.5 履约与完成确认

**设计目标**
使双方对任务是否开始、是否完成有一致记录，减少口头沟通造成的状态不一致。

**触发路径**
「我的任务」→ 进行中任务 →「提交完成」→ 发布者确认完成。

**交互流程**
1. 承接者完成任务后提交完成说明。
2. 任务进入“待完成确认”。
3. 发布者核对交付结果并确认完成；若有分歧，可发起争议。
4. 确认完成后状态变为“已完成”，进入评价环节。
5. 超时未确认时按后续制定的提醒与人工处理规则处理，不直接自动认定某方违规。

**页面设计**
- 清楚展示当前待谁操作及下一步操作。
- 完成说明只收集处理任务所必需的信息；上传图片等能力需另行评估隐私和存储风险。
- 争议入口应在完成确认页可见。

**验收重点**
- 任务状态变更有操作记录。
- 争议未解决前，不生成确定性的负面信用结论。
- 重复提交完成操作不会造成重复状态变更。

#### 5.2.6 取消、举报与申诉

**设计目标**
为任务取消、疑似违规和履约争议提供一致、可解释、可追溯的处理路径。

**触发路径**
任务详情或「我的任务」→「取消任务」/「举报」/「申请复核」。

**交互流程**
1. 用户选择操作类型及原因，并提交必要说明。
2. 系统检查当前状态、发起人权限及是否允许取消。
3. 对一般取消，记录原因、更新时间并通知另一方。
4. 对争议或安全举报，进入待处理队列，保留必要日志。
5. 由授权人员根据规则和证据人工复核；处理结果向相关用户说明，并提供申诉路径。

**页面设计**
- 取消、举报和申诉使用不同入口，避免概念混淆。
- 说明哪些内容会被提交、谁可能查看及处理进度如何查询。
- 不公开举报人的非必要身份信息，也不展示未经核实的指控。
- 对紧急人身安全风险提示用户联系当地紧急服务或可信任的校方渠道；平台不宣称可替代紧急救援。

**验收重点**
- 无权限用户不能替他人取消或修改任务。
- 每次操作记录操作者、时间、原因和结果。
- 争议期间暂停自动负面信用影响。
- 人工复核结果可追踪，申诉不因用户提出异议而受到额外惩罚。

#### 5.2.7 履约记录与评价

**设计目标**
让用户通过可解释的历史记录建立信任，同时避免单次误会或恶意评价造成不公平影响。

**触发路径**
任务完成 → 双方评价 →「履约记录」查看历史结果。

**交互流程**
1. 已完成任务开放双方评价。
2. 评价围绕准时、沟通、按约完成等与履约相关的行为。
3. 系统记录评价提交状态及必要的反滥用信号。
4. 用户可对不实、辱骂或涉及隐私的评价举报。
5. 有效申诉由人工复核；争议未处理完前不将相关内容用于确定性的处罚。

**页面设计**
- 评价应有具体维度和适当文字长度限制。
- 不将信用简化为单一公开分数；展示可理解的履约事实与样本背景。
- 新用户显示“记录较少”而非直接贴上低信用标签。

**验收重点**
- 只有符合规则的订单可评价。
- 同一用户不能重复提交同一订单的评价。
- 用户可以查看和申诉与自己相关的履约记录。

### 5.3 AI 能力设计

AI 属于辅助能力，不是首期上线的必要条件。建议先在原型或离线测试中验证其有效性，再决定是否接入模型服务。

#### 5.3.1 能力一：任务描述完善建议

**设计目标：** 帮助发布者发现任务描述中的缺失信息，提高任务可理解性，减少重复沟通。

**触发路径：** 发布任务表单 → 用户主动点击「检查描述」→ 查看建议 → 用户自行修改或忽略。

**输入维度**
- 用户填写的任务类别、标题和描述。
- 用户选择的取送区域、截止时间、预计耗时和报酬。
- 当前任务字段的完整性检查结果。
- 适用的禁止任务规则与安全提示。

输入不应包含完成检查不需要的手机号、学号、精确住址或其他敏感信息。调用外部模型前须说明数据用途，并完成供应商数据处理与隐私评估。

**输出格式**
结构化 JSON（示意）：

~~~json
{
  "status": "suggestions_available",
  "missing_fields": ["delivery_area"],
  "clarifying_questions": ["交付地点是否为公共区域？"],
  "rewrite_suggestion": "可选的任务描述改写文本",
  "risk_flags": [],
  "explanation": "建议补充交付区域，以便承接者判断路线",
  "requires_user_confirmation": true
}
~~~

字段含义：
- `status`：检查状态，例如 `ok`、`suggestions_available`、`review_required` 或 `error`。
- `missing_fields`：建议补充的字段列表。
- `clarifying_questions`：帮助用户澄清需求的问题。
- `rewrite_suggestion`：可选改写建议，不自动覆盖原文。
- `risk_flags`：命中的规则类别，不输出未经证实的用户动机判断。
- `explanation`：简短、可理解的原因。
- `requires_user_confirmation`：默认必须由用户确认后才应用建议。

**交互与失败处理**
- 用户可接受、逐项编辑或忽略建议。
- 模型超时、输出格式错误或不可用时，回退到普通必填项校验，不阻塞正常填写。
- 不允许 AI 自动发布任务或替用户承诺报酬、时间和交付条件。

#### 5.3.2 能力二：任务规则与风险提示

**设计目标：** 依据平台明确的任务规则，提示可能涉及危险、违法、违规代购、代签、账号密码交付或其他禁止内容的任务，减少明显违规内容进入平台。

**触发路径：** 用户提交任务前 → 规则检查 → 必要时提示修改或转人工审核。

**输入维度**
- 任务标题、描述、类别和必要的交付说明。
- 由产品与运营维护的规则清单。
- 字段校验结果及有限的任务上下文。

**输出格式**
结构化 JSON（示意）：

~~~json
{
  "decision": "allow_with_notice",
  "rule_codes": ["LOCATION_DETAIL"],
  "user_message": "请使用公共区域或区域级地点描述，避免公开精确住址。",
  "recommended_action": "edit",
  "needs_human_review": false
}
~~~

- `decision`：仅使用预先定义的 `allow`、`allow_with_notice`、`block_pending_review`、`review_required`。
- `rule_codes`：命中的规则代码。
- `user_message`：面向用户的简明解释。
- `recommended_action`：如 `continue`、`edit` 或 `contact_support`。
- `needs_human_review`：是否需要授权人员复核。

**决策边界**
- 明确的禁止规则应优先由可测试的规则引擎执行；AI 只用于辅助识别表达多样的描述。
- AI 的提示不是违法认定，也不能自动认定用户有恶意。
- 可能造成用户权益影响的拦截、封禁或信用处罚必须提供理由与复核渠道。
- 对不确定结果采用提示补充或人工复核，而不是无解释地永久封禁。
- 不将模型输出作为唯一的安全保障；必须有规则测试、人工抽检、误报/漏报监测和版本回滚方案。

#### 5.3.3 AI 质量评估要求

上线前应建立人工标注测试集，覆盖正常任务、信息缺失、模糊描述、边界案例和禁止任务类别。至少评估：
- 规则类别识别的精确率与召回率。
- 不同任务类型上的误报、漏报。
- 结构化输出格式有效率。
- 建议的可采纳率与用户修改率。
- 平均响应时间、调用失败率和单次成本。

具体阈值需通过试验设定，不在没有测试数据时预先宣称准确率。应保留规则版本、模型版本、测试集版本与变更记录。对用户有明显影响的决定需人工复核。

### 5.4 设计原则

1. **信息充分但不过度收集：** 仅收集完成任务所必需的信息，默认展示区域级位置。
2. **关键条件前置：** 时间、地点、报酬、耗时、交付要求和任务限制应在承接前可见。
3. **状态明确且可追溯：** 每个状态对应清晰的当前责任人、可执行动作和下一步。
4. **用户自主确认：** 费用、交付要求、AI 建议和关键状态变化需由用户明确确认。
5. **可恢复与可申诉：** 错误输入可修改；取消、举报和评价争议有清晰的复核流程。
6. **公平对待新用户：** 不因历史记录少而直接认定低信用。
7. **安全优先于转化：** 不以提高接单率为由弱化禁止任务、隐私保护或风险提示。
8. **渐进式交付：** 先验证核心流程，再引入账号、后端、AI 和交易能力。

### 5.5 产品价值与核心价值考量

产品价值从用户收益、社区信任和实现可行性三个方面衡量：

| 价值维度 | 核心考量 | 设计取舍 |
|---|---|---|
| 效率 | 是否减少找人、澄清和确认状态的时间 | 优先完善任务字段和筛选，不盲目增加复杂功能 |
| 可理解性 | 用户是否能判断任务要求、费用和风险 | 关键条件前置，避免模糊报价和隐含要求 |
| 信任 | 履约信息是否真实、可解释且可申诉 | 使用订单事实和人工复核，不依赖单一评分 |
| 隐私与安全 | 是否只暴露必要信息，是否存在可控的风险处理流程 | 最小化收集，限制精确位置与敏感信息展示 |
| 公平性 | 新用户、取消方和争议双方是否得到一致规则对待 | 公开规则、保留申诉、避免自动定责 |
| 可行性 | 开发与运营成本是否匹配当前验证阶段 | 先静态站与原型，再考虑后端与 AI |
| 可验证性 | 是否能用真实数据判断功能有效 | 通过问卷、可用性测试和试点指标验证，不预设结果 |

**核心价值主张：** 让校园轻量互助任务“说得清、找得到、跟得上、可复核”。用户安全、信息清晰和履约公平是产品长期价值的基础，不应为短期活跃或成交指标牺牲。

## 6. 业务规则与订单状态

### 6.1 订单状态定义

| 状态 | 含义 | 允许的主要操作 |
|---|---|---|
| 草稿 | 任务尚未发布 | 编辑、删除草稿 |
| 待承接 | 任务已发布且尚未确认承接者 | 查看、申请承接、发布者取消 |
| 待确认 | 已有承接申请，等待发布者选择 | 发布者确认或拒绝申请、按规则取消 |
| 进行中 | 双方已确认任务要求 | 执行任务、提交完成、按规则申请取消 |
| 待完成确认 | 承接者已提交完成 | 发布者确认完成、发起争议 |
| 已完成 | 双方完成确认或按未来明确的超时规则处理 | 查看记录、评价、举报评价 |
| 已取消 | 任务终止 | 查看取消原因与记录 |
| 争议中 | 对履约或任务内容存在争议，等待处理 | 补充说明、查看进度、申请复核 |

已完成或已取消的任务不可直接恢复为待承接；如需重新发布，应创建新任务并保留关联记录。所有状态迁移都必须校验操作者权限和当前状态。

### 6.2 取消规则

- 待承接状态下，发布者可取消任务并填写原因。
- 待确认或进行中状态下，取消需记录发起方、原因和时间，并按后续明确的规则通知另一方。
- 对是否应承担费用、是否构成违约等问题，在正式规则与运营能力建立前不自动作出结论。
- 取消规则不得隐藏在长篇条款中；涉及用户义务的规则应在关键操作前展示。

### 6.3 信用与评价规则

- 信用信息应基于可核实的履约记录，不以单一星级替代事实。
- 争议处理中暂停相关负面信用影响。
- 评价只针对与任务履约有关的行为，禁止发布个人敏感信息、辱骂和未经核实的指控。
- 用户可举报评价并申请复核；处理过程保留必要日志。

## 7. 异常和边界处理

| 异常/边界场景 | 系统处理 | 用户反馈与后续措施 |
|---|---|---|
| 必填项缺失或格式错误 | 阻止提交并定位字段 | 保留已填写内容，说明修正方式 |
| 截止时间已过 | 禁止新申请承接 | 提示任务已过期，建议联系发布者或创建新任务 |
| 任务已被其他人确认 | 拒绝重复承接请求 | 刷新状态并提示任务已不可承接 |
| 重复点击提交 | 使用请求去重或状态校验 | 不创建重复任务或重复评价 |
| 网络中断或服务超时 | 不假设操作成功 | 提示重试；后端版本需提供可核实的当前状态 |
| AI 服务超时或返回无效格式 | 回退到基础表单与规则校验 | 明确说明智能建议暂不可用，不阻塞普通编辑 |
| AI 误报或漏报 | 允许修改、申诉或人工复核 | 不以单次模型输出直接作出最终处罚 |
| 任务描述含禁止内容 | 阻止或转人工复核，依规则处理 | 告知具体规则类别及修改/申诉方式 |
| 发布者与承接者对完成状态有分歧 | 进入争议流程 | 暂缓信用惩罚，保留必要操作记录 |
| 用户临时取消或未按时完成 | 记录原因和状态，不自动推断动机 | 按公开规则处理，必要时人工复核 |
| 发现精确住址或联系方式公开 | 提示编辑或限制公开展示 | 仅保留必要数据，按数据策略处理删除请求 |
| 举报涉及人身安全风险 | 提供安全提醒并按权限升级处理 | 不承诺平台可以代替紧急服务或校方处置 |
| 用户要求执行危险或违法任务 | 不提供撮合 | 解释禁止原因，必要时转人工审核 |
| 用户要求删除账号或数据（未来版本） | 按适用规则验证请求并处理 | 明确处理范围、时限和依法需保留的数据 |

## 8. 数据字段与隐私要求

### 8.1 核心任务字段

- `task_id`：唯一任务标识。
- `title`：任务标题，建议 5–40 字。
- `category`：任务类别。
- `description`：任务描述。
- `pickup_area` / `delivery_area`：取件与交付区域；公开页面默认不展示精确宿舍门牌。
- `deadline`：期望完成时间。
- `estimated_duration`：预计耗时。
- `reward`：双方确认的报酬或费用说明。
- `publisher_id` / `runner_id`：发布者与承接者的内部标识。
- `status`：订单状态。
- `created_at` / `updated_at`：创建和更新时间。
- `cancellation_reason` / `dispute_status`：取消原因和争议状态。

### 8.2 数据治理要求

- 明确每类数据的收集目的、访问权限、保存周期和删除机制。
- 不在公开列表展示手机号、学号、精确住址、证件或敏感资料。
- AI 调用遵循数据最小化原则，不向模型发送非必要个人信息。
- 后端实现前应定义访问控制、日志留存、数据导出/删除流程和安全事件响应方式。
- 正式试点前应评估学校规定及适用的个人信息保护、消费者权益、支付与未成年人保护要求。

## 9. 数据指标与验证方法

本阶段不预设业务结果或虚构基线。交互原型与试点阶段建议观测：

- **任务创建：** 表单完成率、字段错误率、放弃率。
- **任务发现：** 列表到详情点击率、筛选使用率、无结果比例。
- **任务匹配：** 详情到申请承接转化率、平均等待时间。
- **履约质量：** 完成率、取消率、超时率、争议率。
- **信任与安全：** 举报率、申诉处理时长、申诉改判率、隐私相关反馈。
- **AI 质量（若启用）：** 结构化输出有效率、规则识别精确率/召回率、误报/漏报、建议采纳率、延迟与成本。

所有指标需定义分母、统计周期和数据来源。样本量不足时应作为探索性观察，不作过度推断。

## 10. 非功能要求

- **可用性：** 核心页面在常见桌面和移动浏览器中可读、可操作。
- **可访问性：** 表单标签明确、错误信息可读、状态不只依赖颜色表达。
- **性能：** 静态首页避免不必要的大型资源；后端阶段需为接口响应时间设定可测试目标。
- **可靠性：** 后端阶段需处理重复请求、并发承接、超时与状态一致性。
- **可审计性：** 关键订单状态变化和人工处理结果可追踪。
- **安全性：** 权限校验必须在服务端执行；不能仅依赖前端按钮隐藏。
- **可维护性：** 规则、状态和 AI 输出使用明确版本管理，避免散落在页面文案中。

## 11. MVP 验收标准

### 11.1 当前静态站验收

1. 首页可在常见桌面及移动端浏览器正常访问。
2. 页面显著标注任务与用户均为示例，不提供真实接单服务。
3. PRD 与需求调研报告链接可访问。
4. 无明显水平溢出、不可读文本或失效的站内链接。
5. GitHub Pages 自动部署工作流可成功运行。

### 11.2 交互原型验收

1. 用户可以浏览任务、使用筛选并查看详情。
2. 用户可填写并预览发布表单，缺失必填项时获得明确提示。
3. 用户可以模拟申请承接、确认、完成、取消和争议流程。
4. 所有模拟操作明确标注为本地演示，不暗示数据已保存到真实服务端。
5. 不允许通过界面操作绕过已定义的状态规则。
6. AI 功能若加入原型，必须可跳过、可忽略，并展示失败回退行为。

## 12. 版本规划

- **V0.1（当前）：** 静态产品页、示例任务、PRD、需求调研报告与免费部署。
- **V0.2：** 可交互前端原型，包含筛选、详情、发布表单和模拟状态流转。
- **V0.3：** 评估并实现后端 API、持久化数据、账号和订单状态机。
- **V0.4：** 举报、申诉、人工审核、履约记录与评价。
- **V0.5（评估项）：** 在隐私、安全和质量验证通过后试验 AI 描述建议与规则提示。
- **V1.0：** 在完成用户调研、校方规则评估、可用性测试和安全检查后，决定是否进行校园试点。

## 13. 待决策事项

以下事项应通过用户调研、原型测试和规则评估确定，不在缺少证据时提前固化：
1. 试点任务类别及任务开放范围。
2. 承接采用申请确认还是先到先得。
3. 报酬表达、取消时间窗口和超时处理规则。
4. 校园身份验证的必要程度及数据保存周期。
5. 评价维度、争议处理时限与人工复核责任人。
6. AI 服务是否必要、模型供应商、数据处理条件及评估阈值。
7. 校园管理规定及真实运营涉及的法律、支付与责任边界。
