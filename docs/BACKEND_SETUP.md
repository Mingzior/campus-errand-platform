# 后端接入计划与部署说明

- **版本：** V0.1
- **状态：** 后端接入准备，尚未连接真实服务
- **适用项目：** 校园搭把手（Campus Errand）

## 1. 当前状态

网站已升级为 V0.2 前端交互原型，支持任务筛选、任务详情、任务发布表单、本地模拟接单、状态流转、取消、完成确认、争议和履约记录。

当前数据保存在访问者自己的浏览器 `localStorage` 中：
- 不会同步到其他用户的设备。
- 清除浏览器站点数据或使用其他浏览器后，记录可能不可见。
- 模拟举报不会发送给真实审核人员。
- 当前没有真实账号、身份验证、服务端数据库或权限系统。

**不要把本地原型当作可处理真实任务或真实交易的平台。**

## 2. 建议后端方案

建议先评估 Supabase（PostgreSQL + Auth + Row Level Security），原因是可从免费额度起步、提供托管数据库和用户认证，并可与静态 GitHub Pages 前端配合。正式选择前仍需核实当时的价格、使用限制、数据区域和服务条款。

建议架构：

1. **前端：** GitHub Pages 静态站点。
2. **身份认证：** Supabase Auth；仅收集试点确实需要的身份信息。
3. **数据存储：** PostgreSQL，保存任务、状态事件和举报工单。
4. **权限：** 所有数据访问均由数据库 RLS 策略控制；不能仅依赖前端隐藏按钮。
5. **关键状态变更：** 使用数据库事务或受控 RPC 函数，保证并发接单时同一任务不会被多人同时承接。
6. **举报与争议：** 写入受限的工单表，仅授权审核角色可访问；举报内容不公开。
7. **运营审核：** 在真实试点前确定有权限的处理人员、处理时限和升级机制。

## 3. 接入步骤

### 第一步：创建 Supabase 项目

1. 在 Supabase 控制台创建项目。
2. 选择符合项目隐私与使用要求的数据区域。
3. 在 SQL Editor 中执行本仓库的 `supabase/schema.sql`。
4. 在 Authentication 中配置所需登录方式和允许的回调地址。
5. 先使用测试账号与虚构任务进行验证，不要导入真实学生资料。

### 第二步：配置前端环境

需要从 Supabase 项目设置中取得：
- Project URL
- Publishable key（或项目当前文档推荐的客户端公开 key）

这些信息需要由项目所有者在确认项目配置后提供，当前仓库尚未配置。**绝不能把 service-role key、数据库密码或其他服务端秘密放入公开的 HTML、GitHub 仓库或浏览器代码。**

GitHub Pages 是静态托管，不提供服务端环境变量。客户端公开 key 只能与正确配置的 RLS 一起使用，不能被当作秘密。生产环境建议用构建流程注入公开配置；所有权限必须由数据库策略保障。

### 第三步：替换本地存储适配器

当前 `index.html` 的数据层使用 `localStorage`。接入时应新增独立的数据访问模块，将以下操作切换为服务端 API：
- 列表查询与筛选
- 创建任务
- 申请承接与确认承接
- 提交完成、确认完成、取消
- 举报与争议记录
- 查询个人任务与履约记录

不要仅把 localStorage 内容上传一次就视为完成后端接入。需要处理加载状态、网络失败、权限错误、重复提交、并发状态冲突和数据刷新。

### 第四步：实现并验证状态机

关键操作应在服务端校验用户身份、角色和当前状态。建议用原子数据库更新或事务/RPC 完成承接，确保只有一个用户可以成功承接同一任务。客户端显示的按钮状态不能作为权限控制。

建议最低测试集：
- 未登录用户不能创建任务或举报。
- 用户不能修改其他用户发布的任务。
- 同一任务的并发承接只允许一个成功。
- 已取消、已完成的任务不能重新承接。
- 只有任务参与者可查看非公开订单详情。
- 举报内容只能被举报人本人（按需要）、提交者和授权审核角色按最小权限访问。
- 争议未处理时不自动施加信用处罚。
- 删除账号或数据时遵守已公布的保留与删除规则。

## 4. 数据模型

`supabase/schema.sql` 提供了初始的 profiles、tasks、task_events 和 reports 表及基础 RLS 示例。正式部署前需要审查策略，并补充受控状态变更函数、速率限制、审核角色配置、数据保留与删除流程。

## 5. 账号、订单与举报的实施顺序

1. **阶段 A — 数据库与权限：** 建表、RLS、基础查询和创建任务。
2. **阶段 B — 账号：** 登录/退出、用户资料最小化、权限校验。
3. **阶段 C — 订单：** 原子承接、状态迁移、取消、完成确认和操作事件。
4. **阶段 D — 举报：** 私有工单、审核权限、处理状态和申诉路径。
5. **阶段 E — 试点准备：** 安全测试、隐私评估、可访问性检查、备份与故障处理。

## 6. 上线门槛

只有在真实后端、身份验证、RLS、订单状态机和举报流程经过测试后，才可以移除页面上的“本地演示”提示。支付、资金托管和自动信用处罚不属于当前接入范围。
